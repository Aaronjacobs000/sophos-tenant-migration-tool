Help and prerequisites

What the tool does, what it needs before you start, and the limits to know about.

What this tool does

It connects to two Sophos Fusion (formerly Sophos Central) tenants, a source and a destination, and moves configuration and devices between them through the public Sophos APIs. It does not copy the whole tenant. You choose what moves and when, and copies and migrations are logged.

  • Endpoint policies: list, compare settings, and clone or overwrite on the destination with their assignments.
  • Web filtering: copy site lists and profiles.
  • Endpoint and user groups: mirror by name and description. Members follow after a device move (see below).
  • Exclusions and lists: scanning, allowed and blocked items, isolation, intrusion prevention, exploit mitigation, Website Management and TLS decryption exclusions.
  • Device migration: the two-tenant migration flow. Devices keep their identity and check in to the destination the next time they are online.

Before you start

  1. Sign in to the source Sophos Fusion tenant as a Super Admin.
  2. Open Global Settings > API Credentials and add a credential with the Super Admin role. Copy the Client ID and Client Secret.
  3. Do the same in the destination tenant.
  4. Instead of steps 1 to 3, you can use one partner or organization credential that manages both tenants, and pick the source and destination from its tenant list.
  5. On both tenants, confirm Device Migration is enabled in Global Settings > Device Migration. Sophos needs the sending and the receiving tenant to allow migration, each within its time window.

The 14-day window

Sophos's device migration needs every selected device to check in within 14 days for the move to land. The tool checks this twice:

  • Devices with a stale last-seen time are greyed out and cannot be selected.
  • The server runs a preflight check before creating jobs and refuses to start if any selected device is outside the window.

If a device does not check in during the window, its entry stays pending on Sophos's side and you will need to queue it again later.

Moving devices

  1. Pick devices on the Endpoints page. Stale ones are blocked.
  2. Press Migrate to open the migration form.
  3. Run a dry run to see the plan without any upstream writes.
  4. Name the job, tick the 14-day acknowledgement and create the jobs. The tool creates a receiving job on the destination, then triggers the sending job on the source with the receiver's handshake token.
  5. The job page shows the sending tenant on the left and the receiving tenant on the right, with a row per device and a ring for the share that has arrived. Sophos reports a device moved within seconds, but the device arrives when it next checks in to the receiving tenant, under a new ID, so each row says waiting for check-in until then. The job is requested until one device has checked in, in progress until all have, then completed. Wall view fits the page to a large screen.

A started migration can't be cancelled: the Sophos migrations API has no cancel or delete, so the move runs to the end. A receiving job that the sending tenant never picks up expires 14 days after it was created.

Checks before a move

The Start migration page runs two read-only checks:

  • Device Migration setting: whether both tenants allow migration, and when that ends. The tool creates no job while either has it off, and it warns when a window closes within a day, because devices that have not checked in by then will not move.
  • Destination licences: free seats against the selected computers and servers, and products the source has that the destination lacks (endpoint and server protection, XDR, MDR, Device Encryption). Product names map loosely to features, so it warns and never blocks.

Group membership

Mirroring an endpoint group copies its name and description only, because member IDs from the source mean nothing on the destination.

When you create a migration job, the tool records the group each device is in. After the move, the Group membership card on the job page adds each moved device to the destination group with the same name, so policies assigned to that group follow it. Mirror the groups first. Groups synced from Active Directory cannot be changed through the API and are reported.

Each device's row has a picker of the destination's groups. It starts on the group with the same name. When there is none, for example a device that was in no group on the sending tenant, or one that went through a tenant without its group and back, it says Pick a group in amber and the device is not added until you pick one. Don't add leaves a device out.

Web filtering

Copy site lists first, then profiles. A profile refers to site lists by ID, and the copy maps each one to the destination list with the same name; a rule whose list is missing is dropped and reported.

When you clone a web control policy that uses a profile, the tool maps the profile ID to the destination profile with the same name. With no such profile the policy is not cloned, and the result names the profile to copy first.

To undo a copy, delete the destination site list or profile from its row menu. A preview runs first, and the destination refuses while a policy uses the profile or a profile uses the list.

Policies

A clone adds each policy's assignments on the destination: device groups and user groups matched by name, users by email and then name, and devices by hostname. Mirror the groups first. A device that has not moved yet is pending: once its move lands, clone the policy again. A policy already on the destination is left as it is, and only its assignments are added. Anything not matched is listed with the reason, and Export assignments (CSV) lists every source assignment for setting by hand.

A Linux runtime detection policy uses a detection profile. The clone points it at the destination profile with the same name, at that profile's latest version. The tool does not copy these profiles: with no such profile the policy is not cloned, and the result names the profile to create on the destination first.

Sophos accepts at most 1000 applications in each application control list through its API, and every write replaces the whole list. A policy with a longer list is not cloned, and the result gives the count.

Order of work

  1. Website Management entries (Exclusions page), because web control policies refer to their tags.
  2. Web filtering site lists, then profiles.
  3. Linux runtime detection profiles, created on the destination by hand, because their policies refer to them.
  4. Groups, then policies, so each policy can be assigned to the groups with the same names.
  5. Other exclusions and lists.
  6. Devices, then group membership from the job page, then clone the policies again to add the devices they are assigned to.

Dry runs

Policies, exclusions, web filtering, device migrations and group membership can be previewed first: the Preview buttons on the Policies, Compare, Exclusions and Web filtering pages, Preview (dry run) on Start migration, and Preview on the job page's Group membership card return the plan the server would carry out without touching the destination. A policy preview lists each assignment it would add and each one it can't match, with the reason. Use them the first few times until you are comfortable with what gets created.

The Groups page has no preview: Mirror writes to the destination as soon as you confirm.

Audit log

Every write to a tenant, from a page or straight through the API, is written as a JSON line to data/audit.log with a timestamp, request ID, side, resource ID, and the result or error. Keep it for change control.

Security

  • By default the server listens only on 127.0.0.1 and is not reachable from the network. HOST and ALLOWED_IPS in .env open it to chosen machines; the README's Using it from other machines explains how.
  • It answers only requests addressed to 127.0.0.1 or localhost, and takes a change only from a page on one of those, so a website can't drive it by pointing its own name at 127.0.0.1 (DNS rebinding). When HOST opens it to the network, the computer's own IP addresses are accepted too, because a rebinding attack needs a name. A change must also come from a page on the tool's own port, so another web app on the same computer can't make one.
  • The tool has no sign-in of its own. Anyone who can reach it acts with the credentials in .env and the ones stored with jobs. Everyone who uses one copy shares its connection and its jobs, and the audit log does not record who made a change.
  • To share it with a team, run it on a server behind your own sign-in, for example a reverse proxy with single sign-on on the same server that forwards to 127.0.0.1:3100. If the proxy passes on its own host name, add that name to ALLOWED_HOSTS in .env (comma-separated). If it sends 127.0.0.1:3100 as the host instead, add the name too, and serve it on port 443 or 80.
  • Credentials are stored in .env at the repo root, which .gitignore excludes. Do not back it up to cloud drives, and run the tool on a workstation with full-disk encryption.
  • The API never returns secrets; the credentials page shows masked values.
  • Destructive actions (delete, overwrite) ask for confirmation.
